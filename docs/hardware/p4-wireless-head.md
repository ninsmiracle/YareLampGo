# ESP32-P4 无线头部板路线（可选，不替换 S3）

这是一条与现有 **S3 + C6 显示屏 + USB 舵机总线** 并存的硬件路线。它不是把旧设备升级成 P4 的覆盖式更新：后端根据配置和设备能力选择传输层，两个固件目标、烧录命令、接线和运行时资产存储都必须保持分开。

## 先选一条路线

| 项目 | 旧硬件：S3 + C6 显示屏 | 新硬件：P4 头部板 + C6 Wi-Fi |
| --- | --- | --- |
| 固件入口 | 固件仓库根目录的 `XIAO_ESP32S3` 与 `ESP32_C6_LCD_1_47_UART/` | 固件仓库的 `ESP32_P4_HEAD/` |
| C6 的职责 | 独立小屏，由 S3 通过 UART 驱动 | P4 的网络协处理器；**不要**烧录 C6 小屏固件 |
| 电机通道 | 电脑 → USB/Feetech 串口 → 底座舵机 | 后端 → Wi-Fi → P4 → 灯头舵机 |
| 表情资产 | 后端 → S3 → C6；C6 确认显示完成 | 后端 → P4 LittleFS；P4 同步启动 LED 和 LCD |
| 后端配置 | `device.motor_transport = "serial"`（默认） | 显式设为 `device.motor_transport = "p4"` |

同一台电脑可保留旧设备的 `~/.lampgo/config.toml`。只有将 `motor_transport` 改为 `p4` 并启用对应 P4 设备后，后端才会尝试无线运动通道；它不会因为发现到 ESP32 而把旧 USB 电机总线自动改成 P4。

## P4 后端配置

先保持旧硬件断电，确认 P4 已烧录 `ESP32_P4_HEAD` 并完成配网。然后在 Web 设置页的“硬件”中保存，或在 `~/.lampgo/config.toml` 写入：

```toml
[device]
motor_transport = "p4"
lamp_id = "AL02"
p4_motion_port = 82

[device_esp32]
enabled = true
preferred_host = "lampgo-p4-XXXX.local" # 也可留空自动发现
mic_enabled = true
```

随后启动：

```bash
uv run lampgo run --web
```

设备状态应显示 `motor_transport: p4`，并且 P4 的 `/device/status` 会声明 `platform: esp32-p4`。这个能力标识决定表情素材采用 P4 直连上传；旧 S3 未声明该标识时，仍使用原有 S3→C6 协议。

## P4 固件与安全边界

### 无线维护与自然位置回位（P4 0.3.4）

本后端与 P4 `p4-head-0.3.4` 使用 `lampgo-motion-v2`，必须配套升级。
旧固件会拒绝新运动协议，不会退回 USB 或跳过校验。现场验收仍需在支撑灯臂、
清空运动范围并可随时急停的条件下进行；编译和软件测试不代表真实动作通过。

**连接方式：电脑 → Wi-Fi → P4 → 五颗舵机。** P4 是唯一舵机总线主控。
不要再把 USB 舵机驱动板与 P4 同时接到总线发送指令。P4 自己的 USB 烧录/日志口
与 USB 舵机驱动板不是同一条链路。插拔舵机线前先断电并支撑灯臂。

已确认的旧故障机制：P4 的反馈读取报文 `FF FF ID 04 02 38 0F checksum` 会进入
USB 驱动板的接收端。电脑 SDK 可能把 `02` 当成 `Angle sen error`，把 `38 0F`
当成型号 `3896`。因此这种组合不能直接证明舵机损坏。USB CLI 会先做短暂静默监听，
遇到未请求数据时停止操作；静默监听只辅助诊断，不替代单主控接线。

**日常回位：** 点击顶部“回到安全位”。普通动作仍限制在校准工作范围内；
超出工作范围但位于有限恢复区间的自然垂落姿态，只允许沿预检轨迹向校准中立位恢复。
恢复区间沿用旧版：最多向工作范围外扩展 1024 编码器刻度，避开 64 刻度的回绕边界。
后端先检查完整轨迹；P4 再核对稳定反馈、范围、零点、目标和扭矩寄存器，
以受限速度/加速度执行，并在实际反馈到位后恢复普通限位。恢复途中断连、
无效回复或方向反转会停止执行；不要用扩大普通工作范围来处理回位问题。

**无线校准：**

1. 保持 USB 舵机驱动板退出总线，启动 `uv run lampgo run --web`。
2. 点击“P4 无线维护”，扶稳灯臂后进入维护；自动动作暂停，P4 确认扭矩关闭。
3. 摆到希望一键回到的中立位，记录中立位，再缓慢活动每个关节到日常使用的两端。
4. 点击“结束采集并预览”。未活动的关节、过小范围、接近编码器边界或中立位靠边都会拒绝保存。
5. 点击“保存并应用校准”，短暂扶稳即可，**无需摆回中立位**。中立位沿用第 3 步的记录，
   不会被保存时的姿态覆盖。P4 检查保存时的真实位置经过零点变换后是否读回一致。旧文件备份到
   `~/.lampgo/backups/calibration/<时间>/`；P4 写入并读回新零点/范围后，后端才替换正式文件。
6. 若保存确认丢失，保留 `.pending-*.json` 和诊断包，不要手工删除旧文件或继续启用动作。
7. 点击“结束维护 / 保持姿态”。工作范围内会在当前位置启用扭矩；范围外保持关闭，随后点击回位。

关闭维护窗口不会开启扭矩。首次设备没有校准文件时，后端只提供维护用配置，普通动作保持禁用。
P4 模式下 `lampgo calibrate` 提示使用网页，不再自动寻找 USB 舵机端口。
有效预览会保存到 `~/.lampgo/maintenance/<lamp_id>.json`，重启后点击“继续上次校准”恢复。
若原校准文件已变动，旧预览自动失效。存在待保存预览时，后端启动不自动开启扭矩。
页面的当前位置、采样范围、中立位均使用采样时的原刻度；内部归一化后的 2047 中立位放在调试详情中。

0.3.3 增加校准失败诊断：`calibration_error` 保留首次失败的舵机、寄存器、写入值与读回值，
`rollback_error` 单独报告回滚核对失败。回滚恢复写入前真实读取的范围、偏移和锁值，
并再次完整读取验证。`rolled_back` / `not_written` 可返回预览；`uncertain` 继续阻止结束维护。
后端保存错误供状态轮询读取，即使网页丢失保存请求的响应，重连后也能取到真实错误。

0.3.4 修复校准寄存器应答超时：实机零点/限位写入应答需约 39–44 毫秒，
原先统一的 15 毫秒等待会误报写入失败，也影响回滚。配置寄存器改为最多等待 100 毫秒，
普通运动反馈仍为 15 毫秒，ID、长度、校验和及舵机状态检查保留。
2026-09-16 已用同一份 398 帧预览完成真机保存，五颗零点读回与正式文件一致；
重新连接后的连续 10 次读取正常，全程扭矩关闭，尚未执行实际回位。
保存后自然姿态处于工作范围外时显示 `recovery_required` 是待回位状态，不表示校准保存失败。

**录制动作：** 保留原有“录制动作”入口。P4 独占读取反馈，维护期间拒绝自动运动。
开始前先回到工作范围；结束后核对当前姿态再保持扭矩。反馈失效会停止采集，
异常录制不能直接保存成可回放动作。回位、录制和新校准分别验收。

**诊断文件：** 日志页点击“下载诊断包”，将整个 ZIP 发给技术人员即可。
运行日志自动保存到 `~/.lampgo/logs/runtime-<进程号>.log`，每段 5 MiB、轮转 3 份；
导出包保存到 `~/.lampgo/diagnostics/`，包含最近运行日志和设备状态。
Windows 对应 `%USERPROFILE%\.lampgo\logs` 和 `%USERPROFILE%\.lampgo\diagnostics`。
导出不包含凭据文件、录音、照片或聊天正文；密钥、鉴权字段和常见敏感参数会脱敏。

回归检查：

```bash
uv run pytest -q tests/test_p4_hal.py tests/test_p4_maintenance.py tests/test_maintenance_api.py
```

实机部署顺序：停止旧后端 → 确认舵机总线只接 P4 → 编译/上传 P4 专用固件（不擦除 NVS）
→ 启动配套后端 → 核对五颗在线、状态和偏移 → 受控回位 → 无线录制 → 最后按需验证无线校准。
不要仅为通信故障覆盖现有 AL03 校准。

P4 的构建、原生 USB、供电和第一次运动说明见固件仓库的 [`ESP32_P4_HEAD/README.md`](https://github.com/shelly-tang/YareLampGo_esp32/tree/main/ESP32_P4_HEAD)。首次切换前必须完成五关节校准、低扭矩无负载动作、LCD/LED 方向、摄像头、音频和配网验证。

P4 是后端与固件配套发布的路线。完成初始配对后，正常 LAN 控制、媒体和资源上传使用设备签发的一次性 nonce 与 HMAC 证明；不要把这套后端和仍在传输可重放配对密钥的旧 P4 固件混用。

不要混用以下内容：

- 不要把根目录的 S3 `scripts/flash.sh` 用于 P4。
- 不要把 `ESP32_C6_LCD_1_47_UART` 烧录到 P4 方案中的 C6。
- 不要把旧 S3/C6 的接线、串口或校准假设直接用于 P4 灯头舵机。
- P4 的原生 USB 调试端口不是旧 Feetech 电机总线；P4 模式下请勿把它填到 `device.motor_port`。

要回到旧硬件，只需恢复 `motor_transport = "serial"` 和对应的 `motor_port`；不需要删除 P4 固件或覆盖旧 S3 配置。

## P4 语音稳定性（0.2.10 起）

P4 固件和后端需要配套升级。稳定通话采用 **16 kHz、单声道 PCM16**，暂不启用端侧 AEC；不以提高音质为目标。

- 麦克风最多发出 8 帧未确认数据，后端消费后逐帧返回确认。浏览器或网络阻塞时丢弃过期音频，不让 TCP 缓冲耗尽 P4 内部 DMA 内存。
- 扬声器分包上限 1920 字节，最多 4 包未确认数据；小窗口流水传输覆盖约 240 ms 延迟。固件播放队列也有明确上限，确认仅代表进入播放队列，不等于已经发声。
- 关闭供电设备的 C6 Wi-Fi modem sleep，避免省电带来的接收延迟；音频连接异常退出后清理会话状态。
- 摄像头 JPEG 按 1 KiB 非阻塞发送，低内部内存时等待，三秒内无法完成则关闭该响应；避免整张图塞入 64 KiB TCP 缓冲后拖住控制接口。拥塞时允许丢帧，不保证音视频无损并发。
- `/device/status` 提供 DMA 低水位、流控暂停计数、扬声器写入字节/非零采样和 I2S 写入失败计数，便于区分网络、播放驱动和实物发声问题。

此协议仅由 P4 握手显式协商，不修改旧 S3/C6 固件。新后端仍兼容没有声明 `ack-v1` 的旧 P4；新 P4 固件则要求配套的流控后端，防止旧发送器再次引发无界积压。麦克风、扬声器、摄像头和 AEC 的并发验收仍须分别记录，不能根据一次 HTTP 成功认定整机通过。

开发者可先关闭网页通话，运行不依赖云端模型的自动链路检查：

```bash
uv run python tools/p4_audio_probe.py --host <P4-IP> --seconds 60 --phases stalled,mic,duplex
```

`stalled` 会故意暂停读取麦克风数据，并检查窗口上限、设备状态及恢复接收；`mic` 为单独收音，`duplex` 为收音加静音播放。加上 `tone` 阶段会发出低音量测试音。工具只打印计数/电平，不保存录音、图片或凭据；凭据读取现有本地配对文件。
